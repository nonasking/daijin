# daijin 오디오 청킹 프로토콜

> 문제: 음성 클립은 수십~수백 KB인데 ESP32의 MQTT 버퍼(PubSubClient)는 작아서 통째로 못 보낸다.
> 해결: 오디오를 작은 조각으로 쪼개 MQTT로 보내고, 받는 쪽에서 이어 붙인다. 양방향 같은 형식.

구현: 디바이스 `sketches/14-daijin/14-daijin.ino`, 브레인 `voice/daijin_mqtt.py`, 디바이스 대역 `voice/test_device.py`.

## 오디오 형식

- 원본: **PCM 16-bit signed little-endian, 16 kHz, mono** (32 KB/초)
- 전선 위: **IMA ADPCM 4-bit** (4:1 압축, 8 KB/초). 바이트 하나에 샘플 둘, **낮은 니블이 먼저 나온 샘플**
- 헤더 협상 없음. 클립의 첫 청크(seq 0)에서 인코더·디코더 상태를 `pred=0, index=0` 으로 맞춘다

### 왜 ADPCM 인가

브로커가 EU에 있어 한국에서 RTT가 약 300 ms다. ESP32 lwIP의 TCP 창은 약 5.7 KB로 고정이라
처리량 상한이 창 ÷ RTT ≈ **19 KB/초**다. 원본 PCM(32 KB/초)은 실시간으로 못 흘린다. 올릴 때도 같은 한계가 걸려
디바이스도 압축해서 보낸다. 압축의 대가는 문자 오류율 약 1%p (같은 발화 144개로 잰 값).

## 토픽

| 토픽 | 방향 | 내용 |
|---|---|---|
| `daijin/audio/in`  | 디바이스 → 브레인 | 녹음 ADPCM 청크 |
| `daijin/audio/out` | 브레인 → 디바이스 | 답변 ADPCM 청크 |
| `daijin/text/in`   | 브레인 → (관찰용) | 전사된 내 말 |
| `daijin/text/out`  | 브레인 → (관찰용) | 다이진의 답(글) |
| `daijin/say`       | 누구든 → 브레인 | 받은 글을 그대로 말한다 |
| `daijin/ask`       | 누구든 → 브레인 | 받은 글을 에이전트에 넣고, 에이전트가 표현해 말한다 |
| `daijin/status`    | 디바이스 → 브로커 (retained) | 디바이스 상태 JSON. 꺼지면 last will 이 `{"online":false}` 로 덮는다 |

## 메시지 (MQTT 메시지 하나 = 청크 하나)

```
바이트 0      clipId   (uint8)   한 음성 클립의 식별자 (0~255 순환)
바이트 1~2    seq      (uint16, big-endian)   청크 순번 0,1,2...
바이트 3      flags    (uint8)   bit0 = 마지막 청크   bit1 = 페이로드가 ADPCM
바이트 4~     payload  ADPCM 데이터, 보통 2048 B (= 4096 샘플 = 256 ms)
```

- **QoS 0.** QoS 1은 청크마다 브로커 왕복 ACK에 묶여 재생 속도를 못 따라간다. TCP가 순서와 전달을 맡는다
- 디바이스의 MQTT 버퍼는 헤더 + 4096 B + 여유. 그보다 큰 메시지는 PubSubClient가 버린다
- bit1이 꺼진 청크는 비압축 PCM으로 읽는다 (구형 호환, 지금은 아무도 보내지 않는다)

### 새 클립의 시작

- **디바이스(수신)**: `seq == 0` 이면 새 클립. 지터 버퍼와 디코더 상태를 비운다. clipId는 보지 않는다
- **브레인(수신)**: clipId가 바뀌었거나 `seq == 0` 이면 새 클립. 디바이스가 재부팅하면 clipId가 다시 0부터라서 seq도 본다

### "답할 것 없음" 신호

브레인이 클립을 버렸을 때(무음, STT 환청) `daijin/audio/out` 에 **헤더만 있는 마지막 청크**를 하나 보낸다:
`[clipId][0][0][flags = 마지막|ADPCM]`, 페이로드 0 바이트. 디바이스는 낮은 단음을 짧게 내고 대기 얼굴로 돌아간다.
이 신호가 없으면 디바이스는 답을 90초 기다린다. 이 신호를 모르는 펌웨어는 길이 검사에서 그냥 무시한다.

## 디바이스 쪽

- **녹음**: BOOT을 한 번 누르면 시작, 한 번 더 누르면 끝. 최소 1초, 12초에서 자동 컷(낮은 "뚜-뚜")
- **캡처**: 전용 태스크가 I2S DMA를 쉬지 않고 비워 0.75초 링에 쌓고, 메인 루프는 링에서 꺼내 인코드·발행만 한다.
  같은 루프에서 TLS 발행(수십~수백 ms 블로킹)을 하면 그동안의 샘플이 유실된다
- **재생**: 2초 링(지터 버퍼)에 디코드한 PCM을 쌓고 0.4초가 차면 재생을 시작한다. 링이 차면 수신 콜백이 재생으로
  비우면서 막히므로 TCP 흐름 제어가 걸린다. 마지막 청크를 받고 링이 비면 끝
- **절전**: 평소 WiFi 절전 ON, 녹음·재생 구간에서만 OFF (절전 중엔 수신이 약 12 KB/초로 묶인다)

## 브레인 쪽

- 청크를 seq 순으로 모아 마지막 청크에서 디코드 → 음량 확인(무음이면 버림) → STT → 에이전트
- 답은 **문장이 완성되는 대로** TTS → ADPCM 청크로 발행한다. 답 하나가 클립 하나이고, 문장 사이에 0.1초 무음을 넣는다
- 디지털 음량(`TTS_VOLUME`)은 인코딩 직전에 곱한다 (작은 스피커의 풀스케일 왜곡 방지)
- 발행은 워커 스레드에서 한다. paho 네트워크 콜백 안에서 발행하면 콜백이 끝날 때까지 실제로 나가지 않아 스트리밍이 무효가 된다

## 시험

```
python3 -m unittest discover -s voice/tests          # 인코더 ⇄ 디바이스 디코더 쌍, 재조립, 신호 (네트워크·하드웨어 불필요)
python3 voice/test_device.py --say "레드 모터 돌려 줘"   # 디바이스 없이 전 구간 왕복 (진짜 브레인이 듣고 행동한다)
```
